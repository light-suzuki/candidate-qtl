# Route B研究担当の会話の切り方と共通の無駄（親エージェント向け）

この文書は、Route Bの親が保存済み科学回答を一括機械処理する手順と、会話コストの比較仮説を区別するための記録である。通常運用への新規採用は#1020/#1023の一括機械処理だけとする。

- 科学方針・採否・Tier・候補の扱いは変えない。正本はそれぞれ [canonical Route B](CANONICAL-ROUTE-B.ja.md) と [Wet採否](CANONICAL-WET-MEMBERSHIP.ja.md)。
- 採用範囲は下記0節で限定する。記録訂正の実測、起動だけの実測、研究全工程で不採用となった案を分ける。後述のコスト式は診断用の仮説であり、採用済みの最適batch値ではない。
- Codex・Claude Code・OpenCode のどれでも、ローカルでもクラウド／Web版のセッションでも同じ考え方で使える。

## 0. 採用する範囲（2026-10-31）

通常運用へ採用するのは、科学判断後の既知記録を一括検査・機械配送する既存経路である。採用後の100gene対応比較では、研究・修復・親の統合・報告を含む総tokensが平均41,923,042→42,533,194.5（**1.46%増**）となり、**全工程の削減は確認できなかった**。

今回のユーザー判断「2%以下の差は利便性で決める」に照らし、理由の配送と操作の利便性を理由に#1020/#1023だけを**採用継続**する。科学的な予測精度の向上や故障率低下を実証した意味ではない。反復別には+0.144%/+2.817%であり、常に2%以内という保証にも使わない。実測・増加理由・採否の記録を参照する。

## 1. 変えないこと

- **文献調査はハーネス組み込みの検索・取得をそのまま使う。** 検索の回数・量・出力形式を節約の対象にしない。調査性能に直結するためで、検索禁止・1遺伝子あたりの上限・検索ノルマは設けない（[通常案件](AGENTIC-QTL-CASE.ja.md)の通常Bの検索）。
- 件数・弱い根拠・予算未消化を理由に、研究を自動で打ち切らない。会話の小分割を新しい既定にせず、調査量を減らさない。
- 論文ID・正確なタイトル、reported gene名・ID・種、9回答、理由、反証、未評価状態を削って削減とは呼ばない。
- 全roster・未評価の`not_evaluated`・lane独立・fresh context（`fork_turns="none"`等）の既存規則はそのまま守る。

## 2. コストの形：どのハーネスでも同じ

どのハーネスも、呼び出しのたびに次をすべて送り直す。

- system
- ツール定義
- 自動で読み込まれる指示ファイル・memory
- それまでの会話履歴

このため、1つの会話のinput総量は、呼び出し回数 n に対しておおむね次の形になる。

```text
C(n) ≈ n·B + g·n²/2
  B : 毎回送る固定部分（system・ツール定義・指示ファイル・memory・task）
  g : 呼び出し1回ごとに履歴が増える平均量（主に前のツール出力）
```

出力を簡素にしても、呼び出しが1回増えれば、その時点の会話長がまるごと加算される。

2026-10-30の研究担当9本（Codex `gpt-6.1-sol`、1実行役・小標本）の再集計では、次のように観測された。いずれも実行役依存の観測で、既定値や保証の根拠ではない。

| 項目 | 観測値 |
|---|---|
| 式と実測の比 | 0.84〜1.02 |
| B | 約42k tokens/回 |
| g | 約5.5k tokens/回 |
| 履歴の再読がinputに占める割合 | 57〜77% |
| outputがinputに占める割合 | 約0.6% |

履歴の再読コストを「出力の文字数 × その後の再読回数」で重み付けすると、内訳は次のとおり。

| 種類 | 割合 |
|---|---:|
| web検索・取得の結果 | 61% |
| ファイル読み | 18% |
| 長時間コマンドのpoll | 6% |
| 書き込み内容のエコー | 5% |
| スクリプトの出力 | 5% |
| ツール探索 | 5% |

web結果の少なくとも20%は、担当がその遺伝子に触れなくなった後も再読され続けていた。

## 3. 親の手順

### 3.1 研究グループごとの会話は比較仮説に留める

web結果は、その遺伝子を判断している間は必要であり、別の遺伝子へ移った後も会話履歴として再送される。この観測だけでは、小分割・新規sessionの方が総tokenを減らすとは結論できない。100gene組合せ試験は総負担が増え、短い監査でもfreshが継続より増えた。元の分割案は今回採用しない。

通常の`--batch-units 20` / `--packing original`を維持する。既存の明示batch分割・lane独立性はそのまま扱い、追加の強制resetや`reference-affinity`への切替をこの文書から要求しない。#1021の「担当分の判断表が完成したら終了」という追加案や別サイズの独立比較は未実証であり、全方式が無効と証明した結果ではない。将来の比較では `context_mode`、`batch_units`、`packing`、batchごとのrequest数とinput/cached/output、研究量を記録する。

### 3.2 1会話の大きさ b の決め方

1unitあたりのコストは次の形になり、在庫理論の経済的発注量（EOQ・平方根公式）と同じ形の最適値をもつ。

```text
c(b) = r·B + g·r²·b/2 + S/b        b* = √(2S / (g·r²))
  r : 1unitあたりの平均呼び出し回数
  S : 担当1本の起動コスト（文献調査に入るまでの呼び出しのinput合計）
```

- **b\* は区間の遺伝子数 N に依存しない。** 総コストはNに比例し、会話の本数はおよそ N/b\* になる。逆に、Nを少数の長い会話へ分けると、1unitあたりのコストがNとともに増える。
- **N=100・1000のような特定の規模を前提にしない。** 実QTLの任意のNに同じbを使う。checkpoint・resumeの都合で100unitずつ別のrun（arm）に区切るのは自由で、bとは独立に決めてよい。
- **B・g・S・r は同じ実行役の自分のrunから測る**（3.4）。過去の観測値ではb\*≈1〜4が推定されたが、研究量の変化を固定していない近似である。100geneで実行した小分割5の組合せは総負担が増えたため、この推定を通常の初期値や科学的最適値として採用しない。
- unitの重さだけで小分割を強制しない。変更の採否は実際のinput/cached/output/requestと研究範囲・原科学記録の保持で判断する。

### 3.3 ハーネス共通の無駄を削る

今回採用するのは、一括機械処理の表示・配送部分だけである。固定部分の変更は実験案として分ける。

- **固定部分 B（今回は不採用）**
  - 最小cwd・自動読込やtool構成の変更は、起動だけでは17.83%減ったが研究全工程の単独効果は未測定である。通常の起動profileを変更せず、既存の盲検性と実際の検索・取得・読み書き能力を保つ。
- **ファイル読み**
  - 担当には自分のbatchの `material.md` だけを渡す。完全資料 `material.full.json` は必要なunit/fieldだけを開く。
  - リポジトリの文書・スクリプト本体を研究担当に読ませない。
- **ツール探索**
  - 使えるツールをtaskに明記し、探させない。
  - ただし、実際にsearch/fetchツールが提供されているかの確認は、親が起動前に行う。
- **poll**
  - 長時間のコマンドを途中で何度も覗かない。出力はファイルへ書き、終了後に件数・失敗だけを見る。
- **エコー**
  - 書いた内容をツール出力で丸ごと返させない。書き込み後の確認は件数・ID・SHAだけにする。
- **スクリプト出力**
  - 確認用のスクリプトは、行数・不一致・失敗IDだけを出す。
- **保存済みの検索結果**
  - 再表示しない。生の検索・取得ログを保存すること自体は維持し、すでに会話にある内容を、保存のために全文で書き出し直さない（ハーネスが許せばコード側で保存する）。

### 3.4 測り方

比較・調整には、総量に加えて次を記録する。

1. 呼び出しごとのinput（会話長）の推移。最初の値が B、平均の増分が g。
2. 文献調査に入るまでの呼び出しのinput合計 = S。担当1本のunit数と呼び出し回数から r を求める。
3. ツール出力の種類別の「文字数 × その後の再読回数」。
4. **調査量**：検索・取得の回数、screenした論文数、採用した論文数。

4 は必須である。会話を小さくすると、担当がより丁寧に調べてtokenが増えることがある。[通常案件](AGENTIC-QTL-CASE.ja.md)の研究段の分割実行の参考例では、batch分割でinputも論文数も増えた。調査量で正規化せずに「分割で増えた／減った」と結論しない。

ハーネスによってnativeログの所在と形式は異なる。クラウド／Web版のセッションでは、手元にログが残らないこともある。取得できない量は `not_measured` と記録し、推定値で埋めない。課金額・利用枠・JSON bytesを総tokenの代わりにしない。cached inputはinputの内数、reasoningはoutputの内数として二重に数えない。

## 4. 未確認のこと

- 研究グループごとの会話が、同じ実行役・同じ凍結material・同じモデル/effortで実際にtokenを減らすか。同時に、9回答・論文・reported gene・反証の輸送と最終Wet保持が変わらないか。
- 研究グループに分けることで、別グループ間で偶然役立っていた検索結果の再利用が失われる影響。
- 他のハーネス・実行役でのB・g・Sの値。

## 5. 保存した科学回答の一括機械処理

研究担当が原回答を保存した後は、`scripts/agentic_route_b.py light-postprocess` で既存の一括検査、保存済みの明示訂正、canonical変換を接続できる。追加のモデル呼出しや科学判断は行わない。`--request` とその `--request-sha256`、新しい `--out` を指定する。明示訂正が既にある場合だけ `--decisions` と `--decisions-sha256` を渡す。書誌cacheと `--offline` は従来converterと同じ意味であり、研究担当の検索禁止を意味しない。

requestのcontractは `agentic-route-b-light-review-request-1.0.0`。`binding` に `bundle/bundle_sha256/light_index/light_index_sha256`、`batches` に全batchの `batch_id/results` を記録する。原本とsnapshotのhashを保存し、stdoutは状態・件数・artifact参照を返す。大量の不備も全件を `corrections.json` へ保存し、返却上限を超えた場合は `narrow_selection_required` と全件の参照先を返す。親は必要なpointerだけを `light-read-source` で読み、正常rawの全文を直後に再表示しない。発見した新資料は従来どおりextend/refreezeしてからimportする。

新しい`resume-plan`、起動profile変更、追加の会話reset/compaction、表示codecは今回採用しない。既存merge/extend/reuse-planは引き続き各契約に従う。transport completedを全memberの科学調査完了とせず、生成物・hashの一致を科学的非劣性の実証と呼ばない。
